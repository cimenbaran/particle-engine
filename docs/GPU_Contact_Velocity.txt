GPU CONTACT VELOCITY RESPONSE

Scope and inputs
GpuContactVelocity is an isolated GPU restitution/friction component exercised
by --gpu-test. Live simulation remains ballistic; S2-07 is not complete.
It consumes immutable predicted and reconstructed ParticleGpu snapshots, the
material table and upstream solver status. Only dynamic-solid velocity xyz may
change. The independent all-pairs algorithm and invariant scope are specified
in Contact_Velocity_Reference.txt.

Constructor profile: capacity 0..1,048,576, common radius 0.0625 m, maximum
prediction-to-correction displacement 0..32 m (default 0.25), contact slop
0..0.0625 m (default 0.0001), finite nonnegative bounce threshold (default 0.5).
Displacement validation includes 1e-5 m allowance. Search support is the maximum
of diameter plus twice that padded bound and diameter plus slop. This retains
predicted contacts even when position corrections separate their endpoints.
The caller must retain prediction's incoming velocities until this pass finishes.

Pipeline and storage
All dispatches execute in one sequential view, with no submit-time allocation or
CPU readback. Clear status; pack/validate; build fresh keys, stable sort, ranges
and exact-key hash from reconstructed state; count degrees; accumulate response;
reduce errors/metrics; publish only when the complete pool is valid.

Packed snapshot uses eight vec4 lanes per slot: 0..3 reconstructed ParticleGpu,
4 predicted position/radius, 5 incoming velocity/inverse mass, 6 immutable
validation/eligibility/restitution/friction, 7 degree/error/candidate/probe data.
Degree traversal reads only immutable lane six of other bodies. Response reads
completed degree rows. Shared neighbor traversal supports a configurable stride,
with four lanes remaining the default for ordinary ParticleGpu consumers.

Two separate 64-byte outputs, 128-byte packed snapshot and 32-byte candidate
result cost 288 bytes per slot plus a 16-byte status and the owned spatial-index
pipeline. Zero capacity uses minimum allocations. At most six compute bindings
are required. An output distinct from both inputs is selected; incompatible
aliases and invalid handles are rejected before dispatch.

Validation and publication
Alive solids require matching full identity, slot ID equal to storage location,
positive generation, radius 0.0625, matching inverse-mass bits, finite positions
and velocities, and displacement within the bound. Inverse mass is zero or a
positive normal finite float. Restitution/friction are finite in [0,1]; negative
subnormal coefficients are rejected by bit checks. Dead slots are excluded before
material access. Liquid/gas/static state retains its bits.

Status words are error bits, maximum degree, maximum candidates, maximum probes.
Errors: 1 upstream failure, 2 index/traversal failure, 4 snapshot/profile/material/
displacement failure, 8 nonfinite response arithmetic. Any error preserves the
entire reconstructed input, including otherwise valid bodies. Candidate updates
are never partially published. The time-step owner must handle the visible error.

Response uses minimum restitution, geometric-mean friction, low-speed bounce
suppression and symmetric degree/mass weights. It uses incoming impact speed to
avoid converting penetration correction into bounce. There is no neighbor cap.
Shared contact normals use explicit xyz components for the coincident ID axis;
this avoids dynamic vector writes inside HLSL variable-length traversal loops.

Validation and remaining work
74 Metal fixtures per workgroup variant compare every output velocity with the
independent CPU reference, check immutable inputs and exact preserved fields,
and exercise dense 1,023-neighbor cells, counts around workgroup boundaries,
extreme normal inverse masses, coefficient/profile faults, overflow, rollback,
recovery, retained/new contacts and the complete position-solve -> reconstruction
-> response GPU chain. Closed collision cases check energy and momentum; isolated
pairs also check tangential non-reversal. These checks do not prove resting-pile
stability or full-step energy behavior. See tests/results/m3-max-contact-velocity.txt.
D3D11 validation, live time-step integration, terrain sweeps, stable piles,
performance budgets and ten-minute granular soaks remain open.
