WINDOWS BUILD AND EXECUTION VALIDATION

The Native build workflow compiles Windows/D3D11 and macOS/Metal packages with
128- and 256-thread compute variants and runs CPU/schema/shader-cache tests.
Compilation alone does not verify GPU execution. A Windows MSVC ambiguity in
the recording profile comparison was found by CI and fixed by extracting the
JSON string explicitly; the malformed-type regression is also covered.

D3D11 software validation
The explicit --software-gpu option is restricted to --gpu-test, --replay or --capabilities:
  ParticleWorld.exe --software-gpu --capabilities warp-capabilities.json
  ParticleWorld.exe --software-gpu --gpu-test
  python tests/replay_regression.py path/to/ParticleWorld.exe out/replay-regression --software-gpu

The app creates a feature-level 11.0 D3D11 WARP device with D3D11CreateDevice and
supplies it as bgfx's external device context. It owns the creation reference
until initialization completes; bgfx retains/releases its own reference. This
avoids relying on the pinned DXGI enumerator's software vendor hint, which can
be overridden when adapter zero is selected. VSync is disabled in this mode.
Capability reports mark software_renderer_requested, and test output identifies
WARP explicitly. This flag records the selected application mode; ordinary
hardware-selection behavior is unchanged. macOS rejects the option.

The Windows CI jobs run this mode from the installed package after CPU tests,
with a ten-minute timeout, and retain capability JSON and GPU-suite output in
WARP-validation-wg128 / WARP-validation-wg256 artifacts. A test failure fails
the job. Initial CI execution of this new software mode is still pending.
WARP can exercise HLSL execution, buffer/image access, readback, ownership,
visibility and shader reload, but it is not hardware performance certification
or proof of all vendor-driver behavior. No benchmark accepts --software-gpu.

Hardware acceptance remains open
On a supported Windows 11 x64 machine, use a clean installed package without
--software-gpu and retain its build.json plus the following results:
  ParticleWorld.exe --capabilities device.json
  ParticleWorld.exe --gpu-test
  ParticleWorld.exe --capacity 1000000 --soak 600 --report million-soak.json
  ParticleWorld.exe --capacity 1000000 --benchmark million --warmup 120 --frames 600

Also run the dual-pool ballistic benchmark with --capacity 100000 and
--cosmetic-capacity 150000; this still has no water solver. Record the exact
GPU/driver, OS, CPU and RAM. Validate native resize/minimize/restore, focus loss,
held-button camera capture/release, pause/step, physical/cosmetic isolation,
record/save/replay and invalid-file recovery. Check both indirect and masked
rendering and both workgroup variants. Retain output and the binary hash for
each tested package. Software results must never be relabeled hardware results.

CI provenance
Run 38295953059 produced both macOS packages successfully. Their executable and
19 shader hashes matched their manifests, and both packages passed the local
Metal GPU suite, including cosmetic isolation. Their manifests truthfully mark
the worktree dirty: the Ninja setup action extracted its executable into the
checkout's untracked ninja-build directory. These artifacts are therefore not
clean-checkout evidence. The workflow now installs Ninja under runner.temp and
checks git status before configuration. Run 38297882620 passed both macOS
builds; the downloaded 256-thread artifact has worktree_dirty=false, matching
executable/shader hashes, and passed the full local Metal GPU suite. Evidence:
tests/results/ci-38297882620-macos-wg256.txt. Windows remains in progress.

HLSL portability follow-up
The Windows jobs in run 38295953059 passed the corrected recording C++ source
but failed compiling cs_audit_state: HLSL rejected a single-scalar uint4
constructor. The finite-state test now compares exponent bits per scalar
component, and the same unsigned-vector broadcast pattern was removed from
pool export and indirect-argument initialization. The full local Metal GPU
suite, including injected NaN/Inf audits, ownership and indirect checks, passes
after these changes. Windows compilation of the fix remains pending.
