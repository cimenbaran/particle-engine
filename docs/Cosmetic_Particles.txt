INDEPENDENT COSMETIC PARTICLES

Interactive runs allocate a second particle engine for ballistic sparks.
It starts empty, defaults to 16,384 slots and has its own state ping-pong,
render/visibility buffers, active/free lists, generations, command queue and
GPU diagnostics. It uses the existing bounded allocator and ballistic shader.
There is no physical-pool fallback: overflow drops effects and increments the
cosmetic pool's cumulative dropped-spawn counter. CPU command quota rejections
are displayed separately. Clearing sparks resets that pool and its counters.

Use the Cosmetic sparks section to queue a burst of 1..4,096 particles with
0.1..10 seconds of lifetime and 0..20 m/s upward velocity. Pausing and stepping
apply to both engines. Emission is queued for the next tick; a paused button
press alone does not spawn particles. The cosmetic queue independently enforces
32 commands and 8,192 requested spawns per tick, with 256 pending commands.
Sparks use the Wood material profile loaded at startup; physical material
reload does not change this independent table. Shader reload stages both pools
in the same transaction. Both use the common camera/culling/draw-mode settings.

--cosmetic-capacity 0..150000 selects the cosmetic capacity. Zero omits its
allocation and dispatches. This option applies to interactive, --frames and
benchmark runs; it is rejected with soak, replay, capabilities and GPU-test
modes. Benchmarks omit cosmetics by default; explicitly supplying a nonzero
cosmetic capacity selects the dual-pool ballistic workload. Soak/replay still
allocate only the physical engine. See Benchmarking.txt for workload details.

Physical scene reset and Empty scene do not clear cosmetics. Clear sparks does
not reset physical state. Their tick counters and stable-slot namespaces are
independent; a slot ID from one pool cannot be used to address the other.
Starting physical recording or replay explicitly clears cosmetics and blocks
new cosmetic emission for the session. Version-1 recordings contain physical
inputs only. The allocation panel sums both engines' requested payload, even
when the cosmetic pool is empty or suspended during recording.

These effects collide with the analytic floor/box and expire independently.
They do not interact with physical particles, consume/produce physical material,
participate in heat or terrain transactions, or implement transparent smoke.
Reaction/explosion emission, dust/smoke rendering, effects in recording files,
and the design's mixed-scene water performance baseline remain future work. The
initial implementation deliberately retains the existing 64-byte state ABI;
a smaller cosmetic layout is a later optimization requiring its own GPU tests.

Validation on Metal
- All six CTests and the CPU-only test passed, including cosmetic CLI bounds
  and incompatible execution-mode rejection.
- --gpu-test fills 127 cosmetic slots beside 129 physical slots, verifies
  independent overflow, expiry, reuse, reset and whole-pool audits. Explicit
  test-only GPU readback proves physical state bytes are unchanged by cosmetic
  operations and cosmetic bytes are unchanged by physical reset/spawn.
- Cosmetic overflow while physical slots are free does not borrow them. A full
  cosmetic pool does not prevent physical spawning into its own free slots.
- Native UI emitted/rendered 1,024 sparks alongside 16,384 physical particles;
  shader reload preserved both pools while paused. Starting recording cleared
  sparks and disabled emission.
- 120-frame runs with cosmetics disabled and at 150,000-slot cosmetic capacity
  shut down cleanly. This checks allocation/lifecycle, not maximum live effects
  throughput. Separate filled dual-pool ballistic timings are now recorded
  in Benchmarking.txt. D3D11 and the mixed water reference scene remain open.

Packaged evidence: tests/results/m3-max-cosmetic-isolation.txt contains the
clean build manifest, executable SHA256 and GPU suite output for implementation
commit 3c3c461. The package ran from /tmp using its own bundled assets.
