INTERACTIVE GRANULAR MODE

Launch and controls
Run ParticleWorld with --granular, or enable "Particle collisions (resets scene)"
in the main panel. The CLI mode defaults to 512 capacity, 256 Sand particles in
a compact drop, cosmetics disabled and a closer orbit view. Explicit --capacity,
--cosmetic-capacity and --scene retain their meanings. The default app remains
ballistic, preserving existing command recordings. Switching solver resets the
selected scene, command queue, tick counter and diagnostic epoch.

Granular scenes/spawns use common radius 0.0625 and density-derived inverse mass.
Scene centre bounds must fit the inset enclosure. Solid spawn brushes are clipped
to it; fully outside brushes and non-solid spawns are rejected visibly. The pool
API keeps radius 0.045 as its default, so existing ballistic/cosmetic commands and
recordings retain their previous state layout and radius.

Every interactive granular tick applies queued commands to the main state, runs
the GPU coordinator, copies its published state into the app's existing ping-pong
buffers while producing render instances, and rebuilds active/free membership.
Culling, indirect/fallback rendering and pool audits consume those main buffers.
The solver's transaction begins after queued commands: failure rolls back physics
and lifetime evolution, not user edits already applied at the tick boundary.

Diagnostics and faults
The panel displays 12 m/s maximum speed, four substeps, four contact iterations,
proposed cap events, maximum contact degree and boundary events from the latest
asynchronous 16-byte GPU sample. Metrics are per sampled tick, not accumulated
counts or performance timing. Failed candidate work can contribute metrics.
A GPU latch retains errors and blocks later physics ticks until Reset scene,
Empty scene or successful scene/mode reset. CPU polling also pauses the UI.
This prevents a catch-up tick from erasing a failure before its readback arrives.
Reset begins a new diagnostic epoch; stale samples cannot relatch the CPU fault.
The controls retain their positions while snapshots are pending.

Pause, single tick, reset, remove, solid spawn and impulse brushes are supported.
The Recording panel explains and disables ballistic capture/replay while granular
mode is active. Shader reload is disabled in this mode until the whole solver can
participate in a single reload transaction. Material reload retains existing
validation. --granular rejects benchmark, replay, GPU-test and capability
report modes rather than labelling their old reports as granular results.

Resource accounting
The allocation panel adds solver payload and the extra diagnostic ring. With
N=max(1,capacity), S=sum over prefix-scan levels of 4*(max(1,count)+groups), and
H=bit_ceil(2*capacity+2), solver bytes are 1312*N + 288 + 4*S + 16*H. This covers
the coordinator/components, both spatial indices, four scans and status buffers;
it excludes driver alignment, shaders/uniforms and pending deferred destruction.
Settling adds 80*N + 96 + 2*S + 8*H bytes for its history, index and fault latch.
The solver, settling, neighborhood and occupancy rings add 256 GPU texture bytes and 192 host
readback bytes.
This is requested payload accounting, not a certified resident-memory budget.

Validation scope
Both Metal workgroup variants passed 25 granular component fixtures and an app
path fixture covering radius, spawn, impulse caps, membership/state audit, removal
and solver reset. CLI option tests preserve existing defaults and reject invalid
mode combinations. A bounded interactive run completed with zero latched errors.
Native UI checks verified toggle, particle rendering, diagnostics, disabled
recording controls, pause, reset and exactly one tick after reset. Panels start
collapsed so they do not obscure the simulation. See the associated local result
file. General pile stability, Windows interactive validation, granular recording,
full hot reload, interior terrain, benchmarks and ten-minute soaks remain open.

Fixed small-scene settling and energy regression checks are now available via
--granular-check; see Granular_Stability.txt for their scope and limits.

Settling candidates
The live granular path advances a separate tracker once per completed physics
tick. The UI reports candidates, acquiring particles and candidates inside the
contact-loss grace interval. Counts are delayed GPU diagnostics. Candidates remain
active particles: they still integrate, collide, render and accept impulses.
Default acquisition requires 30 supported ticks at <=0.05 m/s; retention uses
<=0.1 m/s and up to two missing-contact ticks. See Settling_Candidates.txt.

Scene reset clears history even when slot generations repeat, starts a new
diagnostic epoch and clears both fault latches. Changing to ballistic mode releases
tracker resources. A tracking error invalidates all candidates on the GPU and
remains latched; the UI pauses when its diagnostic arrives. The physics solver
keeps its separate fault latch. Shutdown checks and prints both statuses.

Application-path tests verify a candidate remains in the active list with valid
free-list ownership, an impulse releases it without deleting it, and scene/empty
resets cannot inherit stale history. These checks complement the 45 isolated GPU
tracker fixtures. Deposition and terrain ownership transfer remain Sprint 3 work.

Particle view selects material, speed, spatial-cell or settling colors, including
while paused. See Particle_Debug_Views.txt for legends and validation limits.

--granular --soak now runs a separate granular lifecycle workload; see
Granular_Soak.txt. Its reports include solver and settling faults and coverage.

Neighborhood diagnostics
The interactive UI samples a separate four-word GPU aggregate for the latest
submitted tick. It displays the sample tick, maximum candidate records per query,
maximum hash probes per query, and collected contact solves. Candidates include
self and may fail the distance/contact filter; neither metric is a total pair
count or a cell occupancy measurement. Maxima span all Jacobi iterations and
velocity contact responses across all substeps. The default profile collects
20 contact solves (4 substeps times 4 position solves plus 1 response). They reset
each tick and on scene reset. The existing Contacts value is maximum contact
degree; no neighbor truncation cap is used. Different delayed diagnostic rings
may display different tick snapshots; the neighborhood tick is shown explicitly.

Contact-phase errors are ORed with the existing phase bits and displayed as
partial metrics. The authoritative solver failure latch still pauses publication.
The new aggregate never changes particle state or solver decisions. Its 16-byte
buffer and 64-byte GPU/48-byte host diagnostic ring are included in resource
estimates. Soak mode allocates the ring through the same app owner but does not
sample it; its existing synchronized audit/solver/settling samples are unchanged.

GPU coordinator tests check a closed pair's exact candidate maximum, nonzero
probes, zero-capacity reset, fixed solve counts across multi-tick reuse, error
propagation and recovery. The app-path test checks a tick-tagged ring readback.
Total accepted/candidate pair counts, collision normals and
per-pass timing remain open under S2-10.

Cell occupancy
A second snapshot displays occupied cells, indexed solids, maximum occupancy and
mean occupancy for the last position-solve input. Failed snapshots are shown as
unavailable, not empty. See Cell_Occupancy.txt for timing, validation and limits.
